# Internationalization

Phase 15.4 made every user-facing string in the project translatable, using Django's
standard i18n framework; French stays the **source language** (`msgid`), so a
`locale/<lang>/LC_MESSAGES/*.po` catalog is what actually carries a translation.
Phase 15.5 added a second, fully-translated language (English) plus per-visitor
language resolution and a switcher UI, so the scaffolding is no longer inert.

## Settings

`famille_busson/settings.py`:

- `LANGUAGE_CODE = "fr"` — unchanged, still the source/fallback language.
- `LANGUAGES = [("fr", "Français"), ("en", "English")]` — the languages offered
  site-wide. `SiteConfig.default_language`'s choices are drawn live from this list
  (see [`site_config.md`](site_config.md)).
- `LOCALE_PATHS = [BASE_DIR / "locale"]` — where `.po`/`.mo` catalogs live, one
  `<lang>/LC_MESSAGES/django.po` (Python/template strings) and
  `<lang>/LC_MESSAGES/djangojs.po` (JS strings) per language.
- `django.middleware.locale.LocaleMiddleware` is inserted into `MIDDLEWARE`, after
  `SiteTimezoneMiddleware` and before `CommonMiddleware` — Django's stock language
  detection (session, cookie, `Accept-Language` header, in that order).
- `annuaire.middleware.UserLanguageMiddleware` is inserted right after
  `AuthenticationMiddleware` (it needs `request.user`), which also puts it after
  `LocaleMiddleware` — so it runs second and **overrides** `LocaleMiddleware`'s guess
  with this project's own precedence chain (see below). Because it runs later, its
  activated language is also what ends up in `LocaleMiddleware`'s own
  response-phase `Content-Language` header.

## Language resolution: `annuaire.i18n.resolve_language()`

`UserLanguageMiddleware` calls `translation.activate(resolve_language(request))` for
the duration of the request (deactivating again afterwards). `resolve_language()`
(`annuaire/i18n.py`) tries each of the following in order, using the first valid one
(validated with `get_supported_language_variant()` against `settings.LANGUAGES`):

1. **`request.user.language`** — the authenticated account's own saved preference
   (`Account.language`; see below). Skipped entirely for an anonymous request.
2. **The `django_language` cookie** — set by the `set-language` endpoint below; this
   is what makes a language choice stick for an anonymous visitor too.
3. **`SiteConfig.default_language`** — the site-wide fallback (see
   [`site_config.md`](site_config.md)).
4. **Django's own `get_language_from_request()`** — the browser's `Accept-Language`
   header, falling back to `settings.LANGUAGE_CODE` — this is the last resort and
   never returns nothing, so `resolve_language()` always returns a concrete code.

## `Account.language`

`annuaire/models.py`'s `Account` gained a `language` field: `CharField`,
`blank=True`, `default=""`, choices from the same `_language_choices()` callable
`SiteConfig.default_language` uses. Blank means "no preference saved yet" — not "use
French" — so an account with no saved language falls through to step 2 of the
precedence chain above, not straight to French. Migration
`annuaire/migrations/0025_account_language.py` is a plain `AddField`, no data
migration/backfill.

## The switcher: `/annuaire/langue/`

`set_language` (`annuaire/views.py`, route name `set-language`, full path
`/annuaire/langue/`) is a project-written replacement for Django's stock
`django.conf.urls.i18n.set_language` view — the stock view isn't compatible with this
project's global `LoginRequiredMiddleware` failing closed, so this one is
`@require_POST` + `@login_not_required` instead. It: validates the submitted
`language` field with `get_supported_language_variant()` (400 on an unsupported
code), always sets the `django_language` cookie (via `settings.LANGUAGE_COOKIE_*`),
saves it to `Account.language` too when the requester is authenticated, and redirects
to `next` after validating it with `url_has_allowed_host_and_scheme()` (falls back to
`/` on a missing or unsafe `next`, closing the open-redirect route a raw
`request.POST["next"]` would otherwise open). See
[`permissions.md`](permissions.md) for why it must be public.

`base.html`'s nav-foot and `base_threshold.html`'s threshold-foot both render a
compact "FR"/"EN" toggle: a POST form with a hidden `next` (the current page) and a
hidden `language` (the *other* of the two configured languages) submitting to
`{% url 'set-language' %}`. In `base.html` it sits next to the existing theme-toggle
button; `base_threshold.html` had no theme toggle at all, so it's the first such
control on the login/signup/magic-link/password-reset pages.

## Wrapping strings in code

- **Model fields and anything evaluated at import/class-definition time**
  (`verbose_name`, `help_text`, form `label`, `TextChoices`/choice-tuple labels,
  `ValueError`/`ValidationError` messages raised from a manager or `clean()`) use
  `gettext_lazy as _` — the translation is deferred until the string is actually
  rendered, not baked in at class-body evaluation time.
- **Strings only ever seen inside a view/request handler** (`messages.success/error/
  warning`, `raise PermissionDenied(...)`, `raise ValidationError(...)` from inside a
  view method) use immediate `gettext as _` — there's no lazy-evaluation need once
  you're already inside a request.
- **Ambiguous bare words** use `pgettext_lazy("<context>", "<msgid>")` to give
  translators disambiguating context for two unrelated senses of the same French word.
  Two contexts exist today: `pgettext_lazy("person", "Nom")` (`Person.last_name`, a
  surname) and `pgettext_lazy("chalet", "Nom")` (`Chalet.name`, the chalet's own
  label) — same French word, different meaning, would otherwise collide into one
  ambiguous catalog entry.
- **Templates** use `{% load i18n %}` + `{% translate "…" %}` for a single string or
  `{% blocktranslate trimmed %}…{% endblocktranslate %}` for anything with
  variables/plurals, across all 106 HTML templates and the 16 email HTML/txt bodies.
  `base.html`/`base_threshold.html` render `<html lang="{{ LANGUAGE_CODE }}">` via
  `{% get_current_language %}` instead of a hardcoded `lang="fr"`.
- **JavaScript** (~14 files under `*/static/js/`) calls Django's JS `gettext()`/
  `interpolate()`, which requires the JS catalog script tag below to run first.

## The JS catalog: `/jsi18n/`

`famille_busson/urls.py` wires Django's stock `JavaScriptCatalog` view
(`domain="djangojs"`) at `/jsi18n/`, route name `javascript-catalog`, wrapped in
`login_not_required` — see [`permissions.md`](permissions.md) for why it has to be
public. `base.html`/`base_threshold.html` load `{% url 'javascript-catalog' %}` as the
**first** `<script>` tag, ahead of bootstrap/theme_toggle/any page script, so
`gettext()`/`interpolate()` are available to every other script that follows.

## Compiling catalogs: dev vs. Docker

`.po` files are human/tool-editable text; Django only reads the compiled `.mo` binary
at runtime. Locally, run `uv run python manage.py compilemessages` after editing a
`.po` file (or after `makemessages` below) — there's no autoreload for this, so a
stale `.mo` will keep serving old strings until recompiled.

In the Docker image, `.mo` compilation happens as its own `RUN` step in the
`Dockerfile`, at **build** time — not in `docker-entrypoint.sh` at container start.
This matters because the `worker` service runs with `RUN_STARTUP_TASKS=0` (see
[`deployment.md`](deployment.md#scheduled-tasks)) and is what actually sends
notification emails; deferring compilation to a startup task the worker never runs
would leave every worker-sent email untranslated. `gettext` (the system package
providing `msgfmt`, which `compilemessages` shells out to) is installed via `apt-get`
in the same Dockerfile alongside `tesseract-ocr`. The committed `.po` sources are
tracked in git under `locale/`; compiled `.mo` files are gitignored and never
committed.

A warning-level system check (`annuaire.checks`, id `annuaire.W004`) flags a
configured language whose `.po` exists but has no matching compiled `.mo` — same
"warning, not error" rationale as `W001`-`W003`: checks run before `collectstatic` at
container boot under `set -euo pipefail`, and a missing `.mo` degrades to
source-language rendering rather than crashing, so it can't be fatal, but it's worth
surfacing since it means a configured language is silently not working.

## Extracting new strings: `makemessages`

After adding or changing translatable strings, regenerate the `.po` sources:

```bash
uv run python manage.py makemessages --all --no-obsolete
uv run python manage.py makemessages -d djangojs --all --no-obsolete
```

`--no-obsolete` drops entries for strings that no longer exist in the source, instead
of accumulating `#~` commented-out cruft. Since French is the source language, a
freshly-extracted `msgstr` is empty; `msgen` fills every empty `msgstr` in with a copy
of its own `msgid` (French-to-French, i.e. "translated" to itself) so the catalog has
no empty entries pending a real translation:

```bash
find locale -name '*.po' -exec msgen --no-wrap -o {} {} \;
```

Then `compilemessages` (see above) before running the app, so the new strings
actually render.

## CI gate: catalogs must stay in sync with source

`.github/workflows/tests.yml`'s `lint` job installs `gettext`, compiles the message
catalogs, then re-runs `makemessages --all --no-obsolete` for both domains and diffs
the result against what's committed:

```bash
git diff -I'^"POT-Creation-Date' --exit-code -- locale/
```

The `-I` flag ignores the `POT-Creation-Date` header line, which `makemessages`
rewrites on every run regardless of whether any string actually changed — without it,
the diff would never be clean. If a PR adds/changes a translatable string without
regenerating and committing the catalog, this step fails the `lint` job: run the two
`makemessages` commands above locally, review and commit the resulting `locale/`
diff, and re-push.

## Renamed: `DataCategory.label_fr`/`note_fr` → `label`/`note`

`annuaire/personal_data.py`'s `DataCategory` dataclass fields lost their `_fr` suffix
now that the values are `gettext_lazy`-wrapped and no longer French-only —
`annuaire/templates/annuaire/privacy_notice.html` was updated to match
(`category.label`/`category.note` instead of `category.label_fr`/`category.note_fr`).
See [`privacy.md`](privacy.md) for the personal-data-export feature itself.

## Emails render in the recipient's own language

Notification emails follow the same precedence in spirit: `annuaire/emails.py`'s
`birthday_reminder()`/`new_blog_post()`/`event_announcement()`/`event_reminder()`
wrap their body in `with translation.override(_recipient_language(recipient)):`,
reading `recipient.account.language` and falling back to `settings.LANGUAGE_CODE`.
`account_setup()` (account creation/password reset, keyed on a bare email address
before any `Person`/`Account` link is guaranteed) instead takes an optional
`language: str | None = None` kwarg, passed in by its `annuaire/views.py` callers
from the target `Account`'s own `.language`. See [`emails.md`](emails.md).

## Downloadable artifacts: viewer language vs. frozen French

Two features export data as a file, and they made opposite choices in Phase 15.4:

- **Excel export** (`annuaire/exports.py`'s `EXPORT_COLUMNS` header labels) is wrapped
  in `gettext_lazy`, so a download picks up the active language of whoever downloads
  it.
- **GEDCOM export** (`genealogy/gedcom/`) stays hardcoded French — genealogy
  interchange files are conventionally read by genealogy software expecting stable,
  language-independent tags, so this was a deliberate scope exclusion, not an
  oversight.

## Adding a third language later

English (Phase 15.5) is a working example of exactly this recipe:

1. Add the new `("<code>", "<Name>")` tuple to `settings.LANGUAGES` — this also
   extends `SiteConfig.default_language`'s and `Account.language`'s choices for free,
   since both draw from the same setting.
2. Run the two `makemessages` commands above to generate
   `locale/<code>/LC_MESSAGES/{django,djangojs}.po` skeletons (empty `msgstr` for
   every entry, since French is the source language).
3. Fill in real `msgstr` values by hand (or a first machine pass) — do **not** run
   `msgen` for a language meant to actually be read; `msgen` only makes sense for
   `fr` (source-to-source) as a placeholder against empty entries. `locale/en`'s
   catalogs (972 `django` + 33 `djangojs` msgids) were filled in this way, with no
   entry left empty or `#, fuzzy`.
4. `compilemessages`, then commit both the `.po` sources and the `LANGUAGES` change.

No further code change is needed — every string in scope is already wrapped, and
`resolve_language()`/the switcher/`Account.language` all work off `settings.LANGUAGES`
rather than a hardcoded language list.
