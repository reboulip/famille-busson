# Internationalization

The site can be shown in French or English. It uses Django's standard translation
system.

The text in the code is written in French. French is the **source language**. The
translations are stored in `locale/<lang>/LC_MESSAGES/*.po` files.

## Settings

In `config/settings.py`:

- `LANGUAGE_CODE = "fr"` — the language the code is written in. Do not change it.
- `LANGUAGES = [("fr", "Français"), ("en", "English")]` — the languages the site
  offers.
- `LOCALE_PATHS = [BASE_DIR / "locale"]` — where the translation files are. Each
  language has `django.po` (for Python code and templates) and `djangojs.po` (for
  JavaScript).
- Two middlewares choose the language of each request: Django's `LocaleMiddleware`,
  then our `UserLanguageMiddleware`, which has the final say (see below).

## Language resolution: `annuaire.i18n.resolve_language()`

For each request, the site uses the first of these that is set:

1. **The user's saved language**, if they are logged in and have chosen one.
2. **The `django_language` cookie**, set by the language switch. This remembers the
   choice for visitors who are not logged in.
3. **The site's default language**, from the site settings (see
   [`site_config.md`](site_config.md)).
4. **The browser's language**, or French if the browser's language is not offered.

## `Account.language`

Each account has a `language` field. Empty means "no choice yet", not "French". So an
account with no choice uses the next step in the list above.

## The switcher: `/annuaire/langue/`

A small "FR"/"EN" button at the bottom of the menu switches the language. It is also on
the login pages. It sends a POST request to `/annuaire/langue/`, which:

- checks that the language is offered (error 400 otherwise);
- saves the choice in the cookie;
- also saves it in the account, if the user is logged in;
- sends the user back to the page they were on.

This page is public, so the switch works on the login page too (see
[`permissions.md`](permissions.md)).

## Wrapping strings in code

All text shown to users must be marked for translation:

- **Text defined when the code loads** (model field names, form labels, choices, error
  messages in models): use `gettext_lazy as _`.
- **Text inside a view** (messages, errors): use `gettext as _`.
- **The same French word with two meanings:** use `pgettext_lazy("<context>", "<word>")`.
  For example, "Nom" means a surname for a person (`"person"`) and a name for a place
  (`"place"`). The translator needs to know which one.
- **Templates:** add `{% load i18n %}`, then use `{% translate "…" %}` for simple text,
  or `{% blocktranslate trimmed %}…{% endblocktranslate %}` for text with variables.
- **JavaScript:** use `gettext()` and `interpolate()`. They come from the `/jsi18n/`
  script (see below).

## The JS catalog: `/jsi18n/`

`/jsi18n/` gives the translations to JavaScript. `base.html` loads it near the end of
`<body>`, right before `{% block extra_js %}{% endblock extra_js %}` (and before the
Bootstrap and theme-toggle scripts). It is public, because the login pages need it too
(see [`permissions.md`](permissions.md)).

This placement matters: it only comes *before* scripts that a page adds through
`{% block extra_js %}`. A `<script src="...">` tag placed inside `{% block content %}`
instead loads earlier in the page, before the catalog even exists yet. This is harmless
for a script that only calls `gettext()` inside an event handler (by the time a user can
click anything, the catalog has long since loaded) — but a script that calls `gettext()`
at module-load time (top-level code, run as soon as the script itself loads) throws
immediately and silently kills the rest of its own execution. This broke the Calendrier
page and the presence-calendar widget before Phase 18.7: `unified_calendar.js` and
`presence_calendar.js` both call `gettext()` at module-load time, and `calendar.html` /
`place_list.html` / `place_detail.html` were loading them from inside `{% block content
%}`. The fix — and the pattern to follow for any new page-specific script — is to always
load such scripts through `{% block extra_js %}`, as `calendar.html`, `place_list.html`
and `place_detail.html` do now (matching the pattern `carte.html` and `genealogie.html`
already followed).

## Compiling catalogs: dev vs. Docker

You edit `.po` files, but Django reads compiled `.mo` files. After you change a `.po`
file, run:

```bash
uv run python manage.py compilemessages
```

Otherwise the site keeps showing the old text.

In production, the `.mo` files are compiled when the Docker image is built. The `.po`
files are committed to git. The `.mo` files are not.

If a language has no compiled `.mo` file, the app shows the warning `annuaire.W004` at
startup. The site still works, but that language shows French text.

## Extracting new strings: `makemessages`

After you add or change text in the code, update the `.po` files:

```bash
uv run python manage.py makemessages --all --no-obsolete
uv run python manage.py makemessages -d djangojs --all --no-obsolete
```

`--no-obsolete` removes text that no longer exists in the code.

In the French files, new entries have an empty translation. Fill them with a copy of
the French text:

```bash
find locale -name '*.po' -exec msgen --no-wrap -o {} {} \;
```

Be careful: this command also fills the English files with French text. Then translate
the new entries in `locale/en/` by hand.

Finally, run `compilemessages` (see above).

## CI gate: catalogs must stay in sync with source

The `lint` job in `.github/workflows/tests.yml` runs `makemessages` and checks that the
`locale/` files do not change:

```bash
git diff -I'^"POT-Creation-Date' --exit-code -- locale/
```

(`-I` ignores the date line, which changes on every run.)

If you change text in the code and forget to update the `.po` files, this check fails.
To fix it, run the two `makemessages` commands above, check the changes in `locale/`,
commit them and push again.

## Renamed: `DataCategory.label_fr`/`note_fr` → `label`/`note`

The data categories of the personal data export (see [`privacy.md`](privacy.md)) are
now translated. So their fields are named `label` and `note`, without `_fr`.

## Emails render in the recipient's own language

Notification emails (birthdays, new posts, events) use the language saved in the
recipient's account. If there is none, they use French. Account setup emails use the
language of the new account, if it has one. See [`emails.md`](emails.md).

## Downloadable artifacts: viewer language vs. frozen French

- **Excel export:** the column titles use the language of the person who downloads it.
- **GEDCOM export:** always in French. Genealogy software expects stable values, so
  this is on purpose.

## Adding a third language later

English was added this way:

1. Add `("<code>", "<Name>")` to `LANGUAGES` in `config/settings.py`. The site settings
   and the account settings offer the new language automatically.
2. Run the two `makemessages` commands above. This creates the files
   `locale/<code>/LC_MESSAGES/django.po` and `djangojs.po`, with empty translations.
3. Fill in every translation, by hand or with a tool, then check them. **Do not** run
   `msgen` on these files: it would copy the French text.
4. Run `compilemessages`. Then commit the `.po` files and the `LANGUAGES` change.

No other code change is needed.
